# 0008 — A GitHub Actions pipeline from lint to ECS

Status: accepted

## Context

The application ships as one container image ([0003](0003-single-image.md)) to
AWS ECS. Every change should pass the same checks as on a developer's machine.
There is no AWS account for this project yet, so the pipeline cannot push or
deploy anything.

## Decision

One workflow, `.github/workflows/ci-cd.yml`, on GitHub Actions where the
repository lives, with five stages. GitHub Actions has no stages as such; a
stage is the jobs that share the same `needs`, so they run in parallel, and the
next stage starts only when all of them have passed, as in GitLab:

1. **Lint**, backend and frontend in parallel: ruff, ruff format and mypy;
   ESLint, Prettier and the TypeScript compiler.
2. **Test**: pytest against PostgreSQL started with `docker compose up db`,
   after checking that the migrations match the models (`alembic check`);
   Vitest with coverage, and a check that the generated API types are up to
   date. Both suites fail below 80% coverage.
3. **Build image**: the root `Dockerfile`, started with its database and
   migrations exactly like `make up`, a smoke test of `/readyz`, a page and the
   API, and a Trivy scan that fails on fixable high or critical
   vulnerabilities.
4. **Push to ECR** and 5. **Deploy to ECS**: placeholders that only print what
   they would do, run for pushes to `main` only.

**Deploying takes a click.** The deploy job uses the `production` environment,
which has required reviewers, so the run pauses until someone approves it.
Only one deployment runs at a time, but a run waiting for approval holds up
neither the checks of later commits nor other runs.

Pull requests run stages 1–3. The commands are the README's quality gates, so
a green local run means a green pipeline. Third-party actions are pinned to
commit SHAs, because tags can be moved; Trivy runs as its versioned container
image.

## How the placeholders become real

- **Push**: assume an IAM role through GitHub's OIDC provider (no AWS keys
  stored in GitHub), log in to ECR and push the image built in stage 3, tagged
  with the commit SHA.
- **Deploy**: register a revision of the service's task definition that changes
  only the image; run `alembic upgrade head` as a one-off task of it, so
  migrations run once and before any task runs the new code
  ([0002](0002-reviewed-migrations.md)); update the service, wait until it is
  stable, and fail if the deployment circuit breaker rolled it back.
- With more than one environment, the same image digest is deployed to
  staging first and to production after approval, instead of being rebuilt.

The infrastructure belongs to infrastructure code outside this repository: a
VPC, an ALB with its health check on `/readyz`, an ECS cluster with a Fargate
service, RDS for PostgreSQL, ECR, the database URL in Secrets Manager as
`APP_DATABASE_URL`, and logs in CloudWatch.

## Alternatives

- **AWS CodePipeline**: keeps everything in AWS, but separates the pipeline
  from the pull requests it gates.
- **Running all checks in one job**: fewer runners, but a failure is harder to
  place and nothing runs in parallel.

## Consequences

- Stages 1–3 run for real on every change; stages 4 and 5 show the flow but
  deploy nothing until an AWS account and its infrastructure exist.
- Pinned actions have to be updated by hand.
